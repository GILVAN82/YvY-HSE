# Sprint 3.1 — Persistent agent thread state

## 1. Objective

Provide bounded, PostgreSQL-backed short-term conversation continuity for the existing LangGraph HSE agent. This is thread state only; it is not cross-thread user memory.

## 2. Previous state behavior and audit

Before Sprint 3.1, `HseAgentState` contained run and conversation UUIDs, recent messages supplied by the caller, lifecycle status, step/tool metadata, final text, refusal/error codes, and transient RAG evidence. Each normal invocation constructed fresh state. `conversationId` was passed as LangGraph's `thread_id`, but the compiled production graph had no checkpointer. `MemorySaver` existed only behind a dev/test option and was process-local and volatile. The HTTP request optionally accepted history from the frontend.

The installed `@langchain/langgraph` transitively includes the base checkpoint API and `MemorySaver`, but not a PostgreSQL checkpoint adapter. No additional dependency was required for the minimal state model: persistence is implemented at the runner boundary through the project's existing `pg` pool and migration mechanism. Graph topology and nodes remain unchanged.

## 3. New thread model

`threadId` is the canonical stable UUID. The existing `conversationId` remains a backwards-compatible alias. If both are supplied, they must match. It is a conversation lookup key, never a user, tenant, company, or SQL identifier.

On invocation the runner loads the thread, uses its bounded messages as authoritative context, appends the new user turn, and invokes the unchanged graph. Only a `COMPLETED` run is saved, with the assistant response. Failed, refused, retrieval-failed, or verification-failed turns do not overwrite the last valid checkpoint.

## 4. Thread ID lifecycle

- Supplied by an internal/backend caller or generated by the runner as UUID v4.
- Returned additively as both `threadId` and the legacy `conversationId` in the SSE `done` event.
- Empty, malformed, or conflicting explicit IDs are rejected.
- The frontend may eventually retain and resend `threadId`; no Angular change was made in this sprint.

## 5. Persistence architecture and checkpoint strategy

`PostgresThreadStateStore` provides `load`, atomic `upsert`, and internal `reset`. It is injected into the runner by the LangGraph API path, which also makes mocked stores straightforward in tests. This is a runner-boundary checkpoint strategy rather than LangGraph's native PostgreSQL saver because that adapter is not installed and the current state requirements do not justify another package.

The store uses positional SQL parameters. A successful upsert increments a version and timestamp. There is no public reset or state-inspection endpoint.

## 6. PostgreSQL integration

Migration `002_create_agent_thread_state.sql` adds one isolated table:

- `thread_id UUID PRIMARY KEY`
- `messages JSONB` array
- `context JSONB` object
- monotonic `version`
- `created_at` / `updated_at`

The migration is additive and does not alter the 42 operational HSE tables or RAG tables.

## 7. Persisted state schema

Persisted:

- bounded user/assistant messages
- `lastRagUsed`
- minimal source reference metadata: source ID, citation label, URL, jurisdiction
- version and timestamps

Not persisted:

- embeddings or vector values
- copied RAG chunks or scores
- raw SQL/tool results
- hidden system prompts
- API keys, database URLs, or environment variables
- model/provider handles or callbacks

Known credential assignment and PostgreSQL URL patterns are deterministically redacted before persistence.

## 8. Isolation model

Every read, write, and reset is keyed by a validated UUID and parameterized query. Automated and live tests prove that Thread B receives neither Thread A messages nor LOTO citations, and that returning to Thread A restores its own context.

## 9. RAG interaction

Messages preserve topic continuity; source references preserve citation traceability. Stored chunks are deliberately excluded. The retriever remains authoritative and may retrieve the current LOTO source again on a follow-up. The live test did so on all three Thread A turns.

## 10. State size strategy

The deterministic reducer retains the most recent `MAX_HISTORY_TURNS` messages (currently 30). Older messages are dropped. No LLM summarization is used. A future summarization hook can be considered only if a real need appears.

## 11. Failure recovery

Persistence is commit-after-success. Model, retrieval, graph, or verification failure leaves the prior row unchanged. Store writes use one atomic PostgreSQL upsert. If persistence itself fails, the run returns failure and the pre-existing checkpoint remains intact.

## 12. Concurrency

Different thread UUIDs are independent. Two concurrent requests for the same new or existing thread can both read the same prior version; the last completed upsert wins and one turn can be lost. Distributed locking or optimistic retry is intentionally deferred. Clients should serialize requests per thread.

## 13. Reset and security

`ThreadStateStore.reset(threadId)` is available only to internal code/tests. There is no unauthenticated delete API.

The application still lacks authentication, RBAC, tenant isolation, and row-level security. UUIDs are not authorization. The existing chat endpoint can accept a conversation UUID, so persistent state must not contain sensitive operational records or personal/medical data. Production multi-user exposure requires authentication and ownership checks before thread persistence is considered secure.

## 14. Tests

Automated state tests cover: empty thread, same-thread restore, cross-thread isolation, realistic follow-up context, RAG reference traceability, vector/chunk exclusion, secret redaction, invalid IDs, invocation-boundary survival, model failure recovery, retrieval failure recovery, internal reset, and bounded history. Existing guard, RAG, ingestion, retrieval, and agent suites remain enabled.

Final validation: TypeScript typecheck PASS, production build PASS, complete automated suite 93/93 PASS, and pgvector validation PASS (0.8.6, 1536 dimensions, rollback-only validation writes). Database verification found 42 operational tables, 784 operational rows, 4 RAG documents, 4 RAG chunks, and zero temporary smoke-test thread rows after cleanup.

## 15. Live multi-turn test

OpenAI was configured. A controlled run used two temporary PostgreSQL threads and cleaned them afterward.

- A1 LOTO precautions: `COMPLETED`, LOTO evidence/citation.
- A2 “restoring energy afterward”: same thread restored, LOTO evidence/citation.
- B1 emergency procedure: independent thread, emergency evidence only.
- A3 “who should verify isolation”: Thread A resumed, LOTO evidence/citation.
- Cross-thread citation leakage: false.

## 16. Thread state versus long-term memory

Thread state continues one explicit conversation and is bounded/resettable. Long-term memory would intentionally retain user facts or preferences across independent threads. No long-term, semantic, preference, or embedding memory exists here.

## 17. Known limitations and next phase

- Same-thread concurrent writes are last-completed-write-wins.
- UUID knowledge is not access control.
- No public reset until authentication and ownership exist.
- The legacy orchestrator remains non-persistent; persistent state belongs to the active LangGraph path.

Recommended next phase: **Sprint 3.2 — Controlled Long-Term Memory**, only after its privacy, ownership, retention, and deletion rules are defined.
